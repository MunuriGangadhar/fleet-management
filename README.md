# FleetPulse — Fleet Operations Dashboard

A fleet management dashboard prototype built for the Bytebeam Frontend Engineer
Intern assignment. React + TypeScript on the frontend, Supabase (Auth +
Postgres + Realtime) on the backend, Leaflet/OpenStreetMap for mapping.

---

## 1. Project Overview

### What this is

FleetPulse is a single-tenant internal tool an operations team would use to
watch a small fleet (14 vehicles here: trucks, vans, cars, and EV bikes)
without needing real GPS hardware. Every vehicle, driver, trip, route, alert,
and maintenance record is backed by real rows in Postgres, generated by a
seed script that produces a plausible week of activity — not a hand-written
static mock.

### Main product decisions

- **The map is the anchor of the dashboard, not a widget bolted onto a
  table.** The main dashboard is a three-pane layout: live fleet map,
  searchable/sortable vehicle list, and an open-alerts feed, all on one
  screen so an operator never has to click through to "see the fleet."
- **A composite health score instead of raw telemetry dumps.** Rather than
  showing 10 raw numbers per vehicle, every vehicle gets one 0–100 health
  score (fuel/battery, open alerts, maintenance status, connectivity) with a
  visible breakdown of *why* it's low. This directly answers "does anything
  need attention" at a glance — the score is **recomputed live on the client**
  from current data rather than trusting a stored column that could go stale
  between page loads (see [`src/lib/healthScore.ts`](src/lib/healthScore.ts)).
- **Route playback, not a static polyline.** Trip detail pages let you scrub
  or play back a trip's actual recorded path, color-coded by speed band, so
  an operator can see *when* a vehicle was speeding or idling, not just *that*
  it happened.
- **Alerts are actionable, not just informational.** Every alert can be
  resolved directly from the dashboard or the alerts page, backed by a real
  RLS-protected `UPDATE` against Postgres.
- **A "Live simulation" toggle** in the topbar calls a Postgres RPC every few
  seconds that nudges a couple of active vehicles forward along their route
  and depletes their fuel/battery slightly. Combined with a Supabase Realtime
  subscription, this is what makes the map visibly move during a demo without
  needing a real telemetry feed, a cron job, or an edge function.

### Standout features beyond the brief

The assignment explicitly asks for a *focused* product, so these were kept
tightly scoped and load-bearing rather than decorative:

| Feature | Why it's here |
|---|---|
| **Fleet health score** | Turns 6+ raw signals into one prioritizable number per vehicle. |
| **Live realtime simulation** | Demonstrates Supabase Realtime end-to-end, not just on page load. |
| **Route playback with speed color-coding** | Makes route history *useful*, per the brief's own callout. |
| **Predictive maintenance** | Flags "due soon" / "overdue" service from odometer + service intervals, not just a static field. |
| **Driver safety scoring** | Ranks drivers by overspeed events per 100 km — useful for coaching conversations. |
| **CSV trip export** | A real operational ask ("give me this in a spreadsheet"). |
| **Smoothed live map markers** | Realtime position updates are tweened over ~900ms (`useAnimatedLatLng`) instead of snapping — a vehicle moving on the map reads as motion, not a teleport. |
| **Cursor-driven 3D card tilt + motion choreography** | Stat cards, page transitions, and list entrances use `framer-motion` for a tactile, GPU-accelerated feel without a 3D engine (see Technical Decisions). |
| **Dark / light theme** | Ops dashboards run on wall-mounted monitors and laptops alike. |

### Intended operator workflow

1. Log in → land on the **Dashboard**: stat row flags how many vehicles need
   attention, the map shows everyone's current position, the vehicle list is
   sorted worst-health-first by default.
2. Click a vehicle in the list (or on the map) to select/focus it, or hit the
   chevron to open its **full detail page**: current telemetry, live map,
   trip history, and predictive maintenance status.
3. Open any trip to **replay its route**, see where it sped or idled, and
   export it as CSV.
4. Check **Alerts** for anything critical fleet-wide; resolve what's been
   handled.
5. Check **Drivers** to see who's driving unsafely (frequent overspeeding)
   or well.

## 3. Local Setup

### Prerequisites

- Node.js 20+ and npm
- A free [Supabase](https://supabase.com) account/project

### Install

```bash
cd fleet-dashboard
npm install
```

### Configure environment variables

```bash
cp .env.example .env
```

Then fill in `.env` — see [Supabase Setup](#4-supabase-setup) below for where
each value comes from:

| Variable | Used by | Where to find it |
|---|---|---|
| `VITE_SUPABASE_URL` | Browser app | Supabase Dashboard → Project Settings → Data API → Project URL |
| `VITE_SUPABASE_ANON_KEY` | Browser app | Project Settings → API Keys → `anon` `public` key |
| `SUPABASE_URL` | `scripts/seed.ts` only | Same as `VITE_SUPABASE_URL` |
| `SUPABASE_SERVICE_ROLE_KEY` | `scripts/seed.ts` only | Project Settings → API Keys → `service_role` `secret` key |
| `SEED_DEMO_EMAIL` / `SEED_DEMO_PASSWORD` | `scripts/seed.ts` only | Whatever you want the demo login to be |

`.env` is git-ignored. The service role key bypasses Row Level Security and
must never reach the browser bundle — it is only read by `scripts/seed.ts`,
which runs in Node, not in the app.

### Run it

```bash
npm run seed   # populates Supabase with drivers, vehicles, trips, alerts...
npm run dev    # starts the app on http://localhost:5173
```

Log in with the credentials `npm run seed` prints at the end.

Other scripts: `npm run build` (production build), `npm run lint`
(oxlint), `npm run preview` (preview a production build locally).

## 4. Supabase Setup

### 4.1 Create the project

1. [supabase.com](https://supabase.com) → New Project. Pick any region,
   set a database password (you won't need it directly — the JS client uses
   API keys, not the Postgres password).
2. Wait for provisioning, then go to **Project Settings → Data API** and
   **API Keys** to collect the four values in the table above.

### 4.2 Create the schema

Open **SQL Editor → New query**, paste the entire contents of
[`supabase/schema.sql`](supabase/schema.sql), and run it once. It creates:

- **Tables:** `profiles`, `drivers`, `vehicles`, `geofences`, `trips`,
  `trip_points`, `alerts`, `maintenance_logs`.
- **Relationships:** `vehicles.driver_id → drivers`, `trips.vehicle_id →
  vehicles`, `trips.driver_id → drivers`, `trip_points.trip_id → trips`
  (cascade delete), `alerts.vehicle_id → vehicles`, `alerts.trip_id →
  trips`, `maintenance_logs.vehicle_id → vehicles`.
- **Auth wiring:** a trigger that inserts a `profiles` row automatically
  whenever a new `auth.users` row is created.
- **Row Level Security** on every table (see §5, Technical Decisions, for the
  policy design and why).
- **Realtime:** adds `vehicles` to the `supabase_realtime` publication so
  UPDATE events push to connected clients.
- **A `advance_fleet_simulation()` RPC**, `SECURITY DEFINER`, granted to
  `authenticated`, powering the "Live simulation" toggle.
- **Two aggregation views** — `vehicle_open_alert_summary` and
  `driver_trip_stats` — that compute per-vehicle open-alert counts/severity
  and per-driver trip totals in Postgres (see §5) instead of the client
  fetching every row and reducing it.

The script is safe to re-run (`IF NOT EXISTS` / `OR REPLACE` throughout,
except policies, which are dropped and recreated).

### 4.3 Seed data

```bash
npm run seed
```

This is a TypeScript script (`scripts/seed.ts`, run via `tsx`) that, using
the service-role key:

1. Creates (or reuses) the demo login user.
2. Clears any previous seed data so the script is idempotent.
3. Inserts 11 drivers and 14 vehicles (trucks, vans, cars, EV bikes — some
   fuel-powered, some battery-powered, on purpose — see §5).
4. Generates 4–8 trips per vehicle over the last ~6 days. Each trip is built
   by [`scripts/lib/generateTrip.ts`](scripts/lib/generateTrip.ts): a
   multi-waypoint route around real Bengaluru localities, walked forward in
   ~15-second steps with an acceleration/cruise/deceleration speed profile,
   randomly inserted traffic halts, and occasional overspeed bursts — not a
   straight line with fabricated stats.
5. Derives fuel/battery depletion, odometer, alerts (low fuel/battery,
   overspeeding, excessive idling, offline, maintenance due), and
   maintenance records **from that generated telemetry**, so the numbers you
   see in the UI are consequences of the data, not independently invented.
6. Prints a summary and the demo login credentials.

### 4.4 If the map doesn't move with "Live simulation" on

Realtime requires the `vehicles` table to be in the `supabase_realtime`
publication. `schema.sql` does this via `ALTER PUBLICATION ... ADD TABLE`,
but if your project has replication managed through the dashboard toggle
instead, go to **Database → Replication**, find `vehicles`, and enable it
there too — either path edits the same publication.

## 5. Technical Decisions

### Architecture

- **Vite + React 19 + TypeScript**, path-aliased (`@/`) `src/` tree split by
  concern: `lib/` (pure functions, no React), `hooks/` (data fetching via
  TanStack Query + Supabase, one hook per resource), `components/`
  (presentational, grouped by feature area), `pages/` (route-level
  composition only).
- **TanStack Query** for all server data — cache-first reads, mutation +
  invalidation for writes, and a direct cache patch in
  `useRealtimeVehicles.ts` so a Realtime event updates the UI without a
  refetch.
- **Tailwind CSS v4** with CSS-variable design tokens (`src/index.css`) so
  the entire dark/light theme is ~60 lines of variables, not duplicated
  utility classes.
- **No global client state library.** Auth session and theme are the only
  cross-cutting client state, both handled with small context providers —
  Redux/Zustand would be overkill at this scope.
- **Route-based code splitting.** Every page is `React.lazy`-loaded
  (`src/router.tsx`) behind a `Suspense` boundary, and the map/motion vendor
  chunks are split out explicitly in `vite.config.ts`. The initial bundle
  loads the shell and login only; Leaflet and the map only load once you
  navigate somewhere that needs them.
- **Two-tier error boundaries.** One around the whole app (`App.tsx`) and
  one inside `AppShell` around just the routed page — a crash in a single
  page shows a recoverable error card without losing the sidebar/topbar or,
  worse, the whole app.
- **Motion, not a 3D engine.** Card tilt, animated counters, page
  transitions, and list stagger all run on `framer-motion` driving CSS
  transforms — GPU-accelerated, no separate render pipeline. A real 3D
  library (`@react-three/fiber`) was evaluated for the login screen but
  dropped: it currently has a peer-dependency conflict with React 19.3, and
  pulling in Three.js for a decorative background wasn't worth ~600KB for
  what CSS `perspective`/`rotateX`/`rotateY` already does convincingly (see
  `src/components/auth/FleetScene.tsx`).

### Data model

The schema is intentionally normalized around **trips as the unit of
activity**, with `trip_points` as a separate breadcrumb table rather than a
JSON blob column:

- Keeps `trips` queryable/sortable by real columns (distance, duration,
  overspeed count) instead of unpacking JSON per row.
- Lets `trip_points` be indexed and paged independently — a trip with 150
  breadcrumb points doesn't bloat every `trips` list query.
- Alerts reference an optional `trip_id` so an "overspeeding" alert can deep
  link straight to the trip that caused it.
- Vehicles carry **either** `fuel_level` **or** `battery_level` (mutually
  exclusive per row, enforced by seed data, not a DB constraint) to reflect
  that a real vehicle is one or the other, not both — a deliberate,
  small realism choice that also exercises "N/A" states in the UI.
- `vehicles.health_score` exists in the schema as a stored column but the UI
  **never reads it** — it's left at its default and the dashboard always
  computes health live from current fuel/battery/alerts/maintenance (see
  `src/lib/healthScore.ts`). This is a conscious tradeoff: a stored score
  would need a trigger or scheduled job to stay correct as alerts are
  resolved in real time; recomputing client-side is cheap at this fleet size
  and can never be stale. Documenting it here rather than silently leaving
  an unused column.
- **Aggregation pushed to the database.** `vehicle_open_alert_summary` and
  `driver_trip_stats` (both Postgres views, `security_invoker = true` so
  they enforce the same RLS as their base tables) compute per-vehicle open
  alert counts/severity and per-driver trip totals server-side. The
  frontend hooks (`useVehicles.ts`, `useDrivers.ts`) query the view instead
  of fetching every `alerts`/`trips` row and reducing it in JS — the pattern
  that keeps working once the fleet is 50x bigger, not just at 14 vehicles.

### Row Level Security

This is a single-tenant internal ops tool, not multi-customer SaaS, so the
policy design is deliberately simple:

- Every table: `SELECT` allowed for any `authenticated` user — an operator is
  trusted to see the whole fleet.
- **Writes are locked down.** Only two client-initiated writes exist in the
  whole app: resolving an alert (`UPDATE` on `alerts`, policy-permitted
  directly) and the live-simulation tick (a `SECURITY DEFINER` RPC, so it can
  update `vehicles` without granting a blanket `UPDATE` policy on that
  table). Everything else — the entire seed dataset — is written with the
  service-role key, server-side, never from the browser.
- `profiles` is the exception: a user can only `SELECT`/`UPDATE` their own row.

### Map library

**Leaflet + react-leaflet + OpenStreetMap tiles.** Chosen over Mapbox/Google
Maps because it needs no API key, no billing account, and no extra setup for
someone reviewing this — `npm install && npm run dev` just works. Custom
`divIcon` markers (not the default Leaflet pin images) avoid the classic
Leaflet-in-a-bundler broken-marker-icon issue entirely, and let status color
and heading rotation be driven by data.

### Notable tradeoffs

- Trip routes are generated by walking a jittered multi-waypoint polyline
  rather than calling a real routing API (OSRM/Mapbox Directions) — keeps
  the project dependency-free and offline-runnable, at the cost of routes
  that approximate roads rather than snapping to them exactly.
- No pagination on vehicles/drivers lists — fine at 14 vehicles / 11 drivers;
  would need it well before fleet size reached the hundreds.
- No test suite. Given the scope and timeline, verification was manual
  (typecheck + build + running the app), documented here rather than
  claimed as automated coverage that doesn't exist.
